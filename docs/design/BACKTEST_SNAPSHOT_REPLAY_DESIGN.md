# 回测与可复现：快照—回放设计（Snapshot & Replay）

> 状态：设计稿（未实施）
> 关联：`docs/roadmap/AGENT_STRATEGY_ROADMAP.md` W2；`docs/design/RESEARCH_CONTINUUM_DESIGN.md`；`docs/midterm/MIDTERM_STATE_DIFF_DESIGN.md`
> 目标：回答"每次跑任务都吃当时接口返回值，如何做可信回测/参数扫描"，并给出泄露防护与版本兼容方案。

---

## 0. 结论摘要

1. **"全量快照 + 只改参数回放"方向正确，但需要拆成两个账本、两种时间、三种回放模式**，否则会把"可复现"和"可回测"混为一谈。
2. **回测的真正难点不是数据不一致，而是"当时到底知道什么"（point-in-time）**。必须用 **双时间建模**（业务时间 vs 获知时间）+ **as-of 连接**，而不是简单存一份"最新返回值"。
3. **版本兼容不靠"让旧快照适配未来所有代码"，而靠**：内容寻址 + schema 版本 + upcaster + **稳定的重放契约** + 执行环境固定 + **分级回放**。
4. **快照只能从"开始快照的那天"保证点时不泄露**；在此之前的历史只能"尽力重建"，必须显式标注不确定。
5. **LLM 是特殊的泄露源**：模型参数里可能包含 as-of 之后的知识。历史回测必须冻结当时的 LLM 输出，或把 LLM 层单独做"影子评估"，不能假装它在历史上是点时安全的。

---

## 1. 先把三个问题分开

| 问题 | 问的是什么 | 需要的机制 |
|---|---|---|
| **可复现（Reproducibility）** | 同一份输入 + 同一版本代码，能否得到同一结果？ | 冻结输入、固定环境、纯函数、注入时钟 |
| **回放（Replay）** | 把一次历史 run 的输入重新喂给（可能改了参数的）引擎，结果如何？ | 输入快照账本 + 参数注入 + 稳定契约 |
| **回测（Backtest）** | 在历史某时点 t，**只用当时可获得的信息**做决策，事后表现如何？ | 双时间 + as-of 查询 + 泄露防护 + 样本外协议 |

> 参数扫描通常只需"回放"（L1）；策略验证必须"回测"（L3）。混用会高估收益：因为回放用的是"今天能拿到的、被修订过的"数据。

---

## 2. 数据源的时间性分类

不同数据源的"易变程度"和"获知时间"完全不同，快照策略必须分类处理。

| 数据源 | 易变/修订 | 业务时间（valid） | 获知时间（knowledge） | 主要泄露风险 | 快照策略 |
|---|---|---|---|---|---|
| 财务报表 | 中（追溯调整、更正） | `end_date` 报告期 | `ann_date` / `f_ann_date` 公告日 | 用"最新修订值"回看历史 | 存原始响应 + `update_flag`；按公告日做多版本 |
| 行情 | 中（复权、停牌、退市） | `trade_date` | 当日收盘/数据入库时间 | 前复权用未来除权事件 | 存未复权 + 复权因子版本；点时股票池 |
| 新闻/公告 | 高（编辑、删除、重发） | `published_at` | 首次抓取时间 / 源站时间 | 用"后来才发的新闻" | 首次抓取即快照 + 内容哈希 + `supersedes` |
| 研报 | 中高（新增、修订、覆盖变化） | `publishDate` | 抓取时间 | 用"回测时能搜到的全部研报" | 存研报列表快照（`infoCode` + 发布日 + 抓取时点） |
| 一致预期 | 高（每日变化） | `as_of_date` | 抓取时点 | 用当前一致预期回看 | append-only 快照（已有 `consensus_snapshots` 雏形） |
| 宏观/行业 | 中（修订、口径变化） | 统计期 | 发布日 | 用修订后数据 | 按发布时间多版本 |
| **LLM 输出** | 高（非确定） | `as_of` | 调用时点 | **模型训练知识含未来** | 冻结请求/响应；历史回测单独处理 |

**关键事实**：如果过去没有快照，今天去 vendor 拉"历史数据"通常只能拿到**当前修订态**，无法还原"当时的原始态"。因此：
- **从启用快照之日起**，可以保证点时正确；
- **此前历史**只能尽力重建，必须标注 `reconstructed=true` 与不确定说明，不能与真实快照混用。

## 3. 信息泄露分类学与防护

| 编号 | 泄露类型 | 例子 | 防护 |
|---|---|---|---|
| L1 | 未来数据 | 用 t 之后才发布的新闻/研报 | as-of 连接：`knowledge_time <= decision_time` |
| L2 | 修订回填 | 用追溯调整后的财报 | 多版本 + 按 `ann_date` 取当时版本 |
| L3 | 幸存者偏差 | 只用"今天仍上市"的股票 | **点时股票池**（退市/停牌按当时状态） |
| L4 | 样本内调参 | 全区间调阈值再同区间评估 | walk-forward + 样本外 + purge/embargo |
| L5 | 标签泄露 | 用未来收益构造特征 | 特征/标签时间严格隔离 |
| L6 | 时点/时区错配 | 收盘后才发的公告算到当天 | 统一交易所时区；收盘后事件顺延到下一交易日 |
| L7 | Vendor 回填 | 供应商悄悄改写历史 | 快照 + 哈希 + 变更告警 |
| L8 | **LLM 知识泄露** | 用 2025 年训练的模型"分析"2020 年事件 | 冻结当时 LLM 输出 / 模型截止日 < 测试期 / 只喂 as-of 证据 |
| L9 | 多重检验 | 反复试规则直到"显著" | 预注册、持有集、多重比较校正 |

**as-of 连接的形式化定义**（双时间）：

> 对决策时点 `t`、数据键 `k`，取满足 `valid_time <= t` 且 `knowledge_time <= t` 的记录中，`knowledge_time` 最大的一条；修订记录通过 `supersedes` 链接形成版本链。

这一条规则同时解决了"报告期 vs 公告日""修订回填""新闻首次出现"三类问题。

## 4. 核心设计：两个账本 + 两种时间 + 三种回放

### 4.1 输入快照账本（Input Snapshot Ledger，WORM）

**定位**：记录"系统当时到底收到了什么"，只追加、不修改。

每条快照建议字段：

```
snapshot_id        内容哈希（如 sha256）
source             tushare / eastmoney / akshare / llm
api                接口/工具名
request            请求参数（含翻页、代码、日期范围）
response_raw       原始响应（字节/JSON/文本）
response_hash      内容哈希（去重与篡改检测）
fetched_at         UTC + 交易所时区
source_event_time  源站给出的业务时间（ann_date / publishDate / published_at）
availability_time  可被系统使用的最早时间（通常 = fetched_at，或源站发布时间）
dedupe_key         业务主键（如 infoCode / (ts_code,end_date,ann_date)）
supersedes         被本快照取代的旧 snapshot_id（修订/重发）
parser_version     解析器版本
schema_version     快照 schema 版本
```

**粒度**：按"请求/文档"存，而不是只按"run"存。一次 run 的 manifest 引用一组 `snapshot_id`，这样跨 run 可复用、可去重。

**为什么存原始响应**：canonical 化规则会变。原始响应 + `parser_version` 才能做"引擎/映射变更回放"（L2）。同时额外存一份**canonical 快照**（带 `adapter_version`）供参数回放（L1）直接使用。

### 4.2 派生帧账本（Derived Frame Ledger）

**定位**：记录"系统当时算出了什么"，用于比对与回归。AlphaBee 已有雏形：`data/midterm/state/<symbol>.jsonl`、`data/midterm/thesis_versions/`、`TaskRecord`。

建议补充的 join 字段：

```
frame_id / run_id
symbol / as_of
input_snapshot_ids[]   本帧消费的全部输入快照
config_hash            本次参数配置哈希
code_version           git commit
adapter_version / parser_version
schema_version
model_id / model_params / prompt_hash / seed
outputs                artifact（FactorSnapshot / CompanyStateArtifact / 报告）
```

**没有这些 join 字段，帧只是"结果"，无法回答"为什么是这个结果"。**

### 4.3 双时间（Bitemporal）

- **valid_time**：业务事实生效时间（报告期、交易日）。
- **knowledge_time**：我们获知/落库时间（公告日、发布日、首次抓取）。
- **decision_time (`as_of`)**：决策时点。

修订不是覆盖，而是**新增版本**：同一 `valid_time`、不同 `knowledge_time`，用 `supersedes` 串起来。回测时按 as-of 规则取"当时最新版本"。

### 4.4 三种回放模式（按问题选择，不要混用）

| 模式 | 输入 | 代码/环境 | 能回答 | 成本 | 适用 |
|---|---|---|---|---|---|
| **L1 参数回放** | 已冻结的 canonical 输入 | 当前引擎代码（契约稳定） | 只改阈值/权重会怎样 | 低 | 日常参数校准、消融 |
| **L2 引擎回放** | 原始快照 | 当前解析/映射 | 改映射/公式/特征会怎样 | 中 | 规则与口径变更验证 |
| **L3 历史重跑** | 原始快照 | **固定当时的代码/依赖/配置/LLM 输出** | 当时到底会怎么决策 | 高 | 发布前验证、真实回测 |

**关键纪律**：
- L1 **只允许改"校准参数"**，不允许改结构（公式形状、状态集合、特征定义）；结构变了就必须 L2/L3。
- L3 若冻结了当时的 LLM 输出，则"LLM 层"是点时安全的；若重跑 LLM，则属于**新实验**，必须单独标记。

## 5. 版本兼容：让快照可重放，而不是"永远兼容所有代码"

用户担心的"版本兼容问题"本质是：**快照格式在变、代码在变、模型在变，旧快照还能不能用？**

答案是：**不要承诺旧快照能被任意新代码重放，而是定义稳定的重放契约与兼容级别。**

### 5.1 四个支柱

1. **内容寻址**：`snapshot_id = hash(content)`，天然去重、可校验，永不变更。
2. **版本标注**：每个快照/帧都带 `schema_version`；每次 run 带执行清单（git commit、lockfile 哈希、Python 版本、config 哈希、model id/params、prompt 哈希、seed）。
3. **Upcaster（升级器）**：读旧 schema 时，用 `v1→v2→…` 的纯函数转换到当前接口；只读转换，**绝不回写旧快照**。每个 upcaster 配单测与黄金样本。
4. **重放契约**：在 **canonical 层**定义稳定接口（例如"一份 FactorSnapshot 的输入字段集合"）。L1 只依赖该接口；接口变更必须走版本化 + upcaster。

### 5.2 兼容策略对比

| 策略 | 做法 | 保真度 | 成本 | 适用 |
|---|---|---|---|---|
| 全环境固定 | 容器/虚拟环境 + git commit + lockfile | 最高 | 高 | L3 发布前验证 |
| 稳定接口 | 只固定 canonical 契约 + upcaster | 中高 | 中 | L1 参数回放 |
| 迁移兼容 | 旧快照升级到新 schema | 中 | 中 | 格式演进 |
| 不保证 | 旧快照仅归档 | — | 低 | 超期数据 |

**建议**：L1 用"稳定接口 + upcaster"（高频、便宜）；L3 用"全环境固定"（低频、严格）；两者共用同一输入账本。

### 5.3 兼容矩阵

维护一张矩阵：`snapshot_schema × adapter_version × engine_version → 支持的 replay_mode`。
当矩阵中出现"不再支持"的组合时，显式登记退役，而不是静默失败。

## 6. 参数注入与确定性（L1 的前提）

**现状问题**（需在 W1/W2 解决）：
- 引擎大量使用**模块级常量**（如 `_BEAT_BONUS`、`TEMPERATURE`、`F_MARGINAL_WEIGHT`），import 期固定，无法在回放时替换。
- 决策路径存在 `date.today()` / `datetime.now()` 缺省（如 `consensus/engine.py`、`midterm/factors.py`、`tracking/scheduler.py`），会导致"同输入不同日不同结果"。

**设计要求**：
1. **参数对象化**：所有可调参数通过显式 `params/config` 注入，禁止在函数内读模块常量。
2. **时钟注入**：`as_of` / `now` 必须由调用方传入；缺省只允许在 CLI 入口，不允许在引擎内部。
3. **确定性排序**：平局、集合遍历、JSON 序列化顺序固定。
4. **随机性**：固定 seed；LLM 温度等参数显式记录。
5. **结构 vs 校准分离**：结构参数变更 → L2/L3；校准参数变更 → L1。

> 这一条是"只改参数回放"能否成立的**硬前提**；否则所谓参数扫描会混入代码/时钟差异。

## 7. LLM 的特殊处理（最容易被忽视的泄露源）

LLM 与普通数据源有三个本质差异：

1. **非确定**：同 prompt 多次调用结果不同 → 不能作为"可复现输入"。
2. **参数化知识**：模型训练语料可能包含 as-of 之后的信息 → 历史回测中"知道未来"。
3. **版本漂移**：模型/prompt 升级会改变判断，但旧快照无法自动适配。

**设计选择**：

| 场景 | 做法 |
|---|---|
| 复现历史 run | 冻结当时的 `request` + `response`，回放时**直接复用响应** |
| 参数回放（只改阈值） | LLM 输出视为固定输入，不重跑 |
| 改 prompt/模型 | 属于**新实验**，单独标记，不与旧结果混比 |
| 历史回测 | LLM 节点要么用"当时冻结输出"，要么用截止日 < 测试期的模型；否则只能做**规则层回测 + LLM 影子评估**，不能声称端到端点时安全 |
| 降低泄露 | Prompt 强约束"只使用提供的证据"；对 LLM 结论做证据回链校验；把 LLM 限定在综合/解释，不参与数值 |

**结论**：L3 的"严格回测"应优先评价**规则/数值层**；LLM 层的价值用影子对比（shadow）衡量，而不是把它当成点时可复现的组件。

## 8. 与 AlphaBee 现状的映射

### 8.1 已有资产（可复用）

- `data/midterm/state/<symbol>.jsonl`：append-only 帧，已是派生账本雏形。
- `data/midterm/thesis_versions/<symbol>.jsonl`：thesis 版本链（反漂移）。
- `data/consensus_snapshots/<code>.jsonl`：一致预期 append-only 快照，已是输入账本雏形。
- `TaskRecord` / `Run` / `Step` / `Artifact`：执行与产物契约。
- `midterm/marginal_shadow.py` + `scripts/f_marginal_shadow.py`：影子回放/统计的起步。
- `scripts/calibrate_tracking_thresholds.py`：离线回放告警的起步。

### 8.2 主要缺口

1. 帧未记录 `input_snapshot_ids` / `config_hash` / `code_version` / `model` 等 join 字段。
2. 新闻/研报没有"首次抓取"快照；只有当前可检索状态。
3. 决策路径存在 `date.today()` 缺省；引擎参数未对象化。
4. 没有 As-of Reader（双时间查询）与泄露护栏。
5. 没有兼容矩阵与 upcaster 机制。
6. LLM 请求/响应未统一冻结。

### 8.3 具体主键建议

| 数据 | 业务主键 | 版本键 |
|---|---|---|
| 财报 | `(ts_code, end_date, report_type)` | `(ann_date, update_flag, fetched_at)` |
| 行情 | `(ts_code, trade_date)` | `(adjust_factor_version, fetched_at)` |
| 新闻 | `url` 或 `content_hash` | `(first_seen_at, supersedes)` |
| 研报 | `infoCode` | `(publishDate, fetched_at)` |
| 一致预期 | `(symbol, as_of_date)` | `fetched_at`（已有同日幂等） |

## 9. 分阶段落地（设计级，不含代码）

| 阶段 | 内容 | 退出标准 |
|---|---|---|
| **P0 语义与清单** | 每个数据源的 as-of 语义、主键、版本键；`date.today()`/模块常量审计；参数清单 | 三张清单可评审 |
| **P1 输入账本** | 原始响应 + canonical 快照 + 内容哈希 + run manifest | 每个 run 可追溯到输入快照 |
| **P2 双时间 reader + 泄露护栏** | as-of 连接；修订/首次出现用例；护栏断言 | 修订与延迟发布用例通过 |
| **P3 参数注入 + L1** | 参数对象化、时钟注入；L1 回放与黄金重放测试 | 同快照 + 同代码 ⇒ 逐字节一致 |
| **P4 L2 + 兼容层** | upcaster、兼容矩阵、映射变更回放 | 旧快照可经 upcaster 读取；L2 差异报告可用 |
| **P5 L3 + 样本外** | 环境固定、冻结 LLM 输出、walk-forward + purge/embargo | 完成一轮端到端历史回测 |
| **P6 校准反馈** | 结果反馈层、命中率/校准曲线、参数复核 | 至少一轮阈值复核并登记 |

## 10. 验收不变量

1. **L1 逐字节一致**：同一快照 + 同一引擎版本 + 同一参数 ⇒ 输出完全一致。
2. **无未来数据**：任何被消费的记录都满足 `knowledge_time <= as_of`（可用护栏断言）。
3. **可追溯**：任一帧可反查到输入快照、代码版本、配置哈希、模型/prompt 版本。
4. **修订正确**：as-of 在修订前 → 必须取旧版本；修订后 → 取新版本。
5. **点时股票池**：退市/停牌股票在历史时点按当时状态参与，不回填。
6. **兼容可测**：旧 schema 快照经 upcaster 后通过黄金测试。
7. **LLM 标注**：任何重跑 LLM 的实验必须标记 `llm_rerun=true`，不得与冻结输出结果混比。

## 11. 风险与取舍

| 风险 | 说明 | 缓解 |
|---|---|---|
| 存储成本 | 全量原始响应 + 多版本 | 内容寻址去重；冷热分层；按需保留 |
| 版权/合规 | 新闻/研报可存储性存疑 | 保留策略、脱敏、仅内部研究、到期清理 |
| 供应商条款 | 禁止长期留存或再分发 | 法务确认；必要时只存哈希+摘要 |
| 环境固定成本 | L3 容器化较重 | L1 日常 + L3 低频 |
| schema 演进 | upcaster 越积越多 | 设退役策略与兼容矩阵 |
| LLM 非确定 | 无法真正"同输入同输出" | 冻结响应；重跑标记为新实验 |
| 历史不可重建 | 启用前无快照 | 显式 `reconstructed=true`，不用于严格回测 |

## 12. 开放问题（需 owner 裁定）

1. **快照保留期**：新闻/研报存多久？是否只存内部派生物？
2. **ground truth**：校准用状态命中、超额收益、回撤，还是人工标注？
3. **LLM 在回测中的角色**：是否允许冻结输出的"半回测"作为主结论？
4. **L1 的边界**：哪些参数算"校准参数"、哪些算"结构参数"？
5. **历史重建的接受度**：启用前数据是否允许以 `reconstructed` 标注后参与校准（仅形状约束）？

## 13. 对"全量快照 + 只改参数回放"这一设想的评价

**肯定**：这是正确的主干思路，尤其是"冻结输入、只动参数"能显著降低回测复杂度。

**必须补的四点**：

1. **快照要带双时间**，否则无法处理修订与延迟发布，"全量"仍会泄露。
2. **快照要分原始层与 canonical 层**，否则改映射就无法回放，旧快照也难兼容。
3. **参数必须可注入**，否则"只改参数"在现有模块常量结构下做不到。
4. **版本兼容要靠稳定契约 + upcaster + 分级回放**，而不是要求一份快照兼容所有未来代码。

**一句话**：把"全量快照"升级为"**双时间输入账本 + 版本化执行清单 + 分级回放契约**"，W2 才真正可落地。
