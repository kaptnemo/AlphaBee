# Trace Store 产品设计（Core / Profile 分层）

> **状态**：产品设计稿（2026-11-11 初稿；2026-11-13 增补 §4 非侵入性与业务无关性约束；未实施）
> **定位**：定义"一次执行如何被记录成可查询、可追溯、可对账的 trace"的产品能力与契约。
> **范围纪律**：本文**只描述功能与行为契约**，不描述实现（代码结构、文件布局、存储选型、数据库/队列、PR 切分等见后续实施文档）。
> **关联**：`docs/design/APIARY_RESEARCH_OS_DESIGN.md`（§1.3 五种偏差 / §3.3 学习回路 / §8.6 数据边界 / §14 RSI 成熟度）、`docs/design/SCOUT_DEEP_RESEARCH_DESIGN.md`（§2.4 TraceRecorder/TraceReader、§3 发现卡）、`docs/design/SINGLE_FRAME_QUALITY_DESIGN.md`（证据与 claim 口径）、`docs/design/BACKTEST_SNAPSHOT_REPLAY_DESIGN.md`（快照引用）。
> **非目标**：不做 UI/看板、不做评估平台、不做回放执行、不做实时干预、不重建 Langfuse。

## 0. 一页摘要

**产品是什么**：一个**分层的 trace store**——`Trace Core` 提供与领域无关的"执行证据链"能力（身份、span 树、内容寻址、血缘原语、查询、保留、策略），`Domain Profile` 提供领域词汇与校验（例如 AlphaBee 的 artifact / issue / decision / claim / 口径/期间）。运行时是唯一写入方；Scout、Apiary、评估工具、人都是读取方。

**解决的问题**：

1. 现有日志是**平铺事件流**：能 grep、不能按 run / 节点 / span 查询，无法回答"这条结论从哪来"；
2. 执行细节散落在**呈现层**（CLI/Web），脚本与后台任务没有同等记录；
3. 没有**内容寻址**：LLM prompt/response、工具入参出参、原始 API 响应无法按引用取回；
4. 没有**领域血缘**：artifact / issue / decision / claim 与工具调用之间没有可查询的边；
5. 没有**稳定查询契约**：Scout 只能读摘要/文本，无法系统性发现"自己错在哪"。

**核心判断**：Scout 要发现的问题（口径混用、静默降级、论证失配、prompt 不服从、成本异常、覆盖盲区、重试丢失、回归漂移）绝大多数**不在最终报告里**，而在执行过程的中间证据里。因此 trace 必须是**可追到源头 + 可对账 + 可按需下钻**的产品，而不是"更多日志"。

**侵入性约束**：业务零知——采集只发生在稳定的执行边界（节点/子代理/LLM/工具/MCP/API/检索/语义汇聚点），未知类型照常记录、不阻断；新增工具、节点、流程重排不要求修改 trace 或业务代码（详见 §4）。

**产品边界一句话**：trace 是**证据**，不是结论、不是业务状态、不是执行回放；Langfuse/OTel 是**下游视图/导出**，不是事实源。

## 1. 背景与目标

### 1.1 触发问题

- 一次 run 约 10–20 分钟、数百次 LLM 调用、上千次工具调用；失败与失真发生在中间步骤，最终报告只暴露结果。
- 现有可观测手段不足以支撑"发现问题"：
  - 事件日志是平铺的、短保留的、无统一关联 ID；
  - 节点无起止时间与输入/输出指纹；
  - LLM 只有用量，没有内容与参数；
  - 工具只有"调用/返回长度"，没有真实内容；
  - 数据获取只记录失败，且关联字段未填充；
  - 语义产物（artifact/issue/decision）与执行过程之间没有可查询的血缘。
- APIARY §1.3 已指出五种偏差：事件选择、本体、顺序、能力、摘要。**产品目标就是逐个消除它们**。

### 1.2 目标（按优先级）

| 优先级 | 目标 |
|---|---|
| P0 | 任意一次 run 可回答"某条 issue / 某个数字 / 某段结论来自哪个节点、哪次工具/LLM 调用、什么内容" |
| P0 | 采集不改变主流程行为；trace 写失败不影响 run 结果 |
| P0 | 采集对业务非侵入：业务模块 0 行 trace 代码；新增工具/节点/入口 0 改动；未知类型可记录 |
| P0 | 同一输入两次 run 可做 span 级差分，定位"哪一步变了" |
| P1 | Scout 可基于 trace 做系统化发现，且每个发现都能追溯到 span/event/content ref |
| P1 | 领域语义可替换（Profile），Core 不出现任何 AlphaBee 专有词汇 |
| P2 | 可选导出到 OTel / Langfuse / OpenLineage / PROV，供外部工具消费 |

### 1.3 非目标

- 不做 trace 的 UI/看板/搜索前端（可由 Langfuse/其他后端提供视图）；
- 不做评估平台（数据集、评分、标注）；
- 不做执行回放/状态重建（回放依赖快照体系，见 BACKTEST_SNAPSHOT_REPLAY）；
- 不做实时干预（不阻塞、不修改 run）；
- 不记录"结论摘要"来替代证据；
- 不追求"记录每个 Python 函数调用"（只记录有产品意义的执行单元）；
- 不与业务事实源竞争（canonical facts 仍是唯一事实源）。

## 2. 用户与场景

| 消费者 | 核心诉求 | 典型问题 |
|---|---|---|
| **Scout（研究 Agent）** | 系统化发现 pipeline 的失败/盲区/矛盾 | "这条 issue 从哪来？""为什么两个结论冲突？""哪一步静默降级了？" |
| **Apiary（能力发展系统）** | 用 trace 证据支撑缺口判断与能力验收 | "这个缺口在多 run 中重复吗？""新能力上线后同输入表现变了吗？" |
| **评估/回归工具** | 同一输入不同版本的差分与分类 | "输出差异来自模型、prompt、代码还是数据？" |
| **开发者（人）** | 复盘、定位 bug、验证修复 | "修复前后同 payload 的哪个 span 变了？" |
| **运维（人）** | 成本、延迟、错误率、容量 | "哪个节点最贵/最慢/失败率最高？" |
| **未来外部系统** | 通过契约读取 trace 快照 | "给我某标的某 run 的证据链快照" |

**典型场景**

1. Scout 盲读原始数据 → 落稿 → 拉取同标的历史 trace → 对账发现"报告宣称改善真实，但证据日志中有一条被丢弃的反证"。
2. 回归工具对同 payload 的两次 run 做 diff，发现输出差异来自数据快照而非 prompt。
3. 开发者从报告中的一条数字反查到对应的事实来源、API 调用与口径。
4. 运维发现某节点 p95 延迟上升 3 倍，并定位到某次工具重试。
5. Apiary 依据 trace 证据，判断一个缺口是否值得立项。

## 3. 核心概念（产品术语）

| 术语 | 定义 |
|---|---|
| **Trace（追踪）** | 一次执行单元的完整记录容器；由 trace_id 唯一标识；对应一次 run。 |
| **Span（跨度）** | 一次有开始/结束的执行单元（节点、子代理、LLM 调用、工具调用、MCP 调用、API 请求等）；可嵌套。 |
| **Event（事件）** | 瞬时发生的语义记录（产物产生、问题出现、降级、缓存命中、血缘边等）；无持续时间，必须挂在 trace 或 span 上。 |
| **Content Object（内容对象）** | 以内容哈希寻址的不可变内容（prompt、response、工具入参出参、原始响应、结构化输出等）；可被多处引用与去重。 |
| **Tier（分级）** | 内容保留级别：L0 引用 / L1 元数据 / L2 内容 / L3 原始快照。 |
| **Lineage Edge（血缘边）** | 两个语义对象之间的关系（生成、使用、派生、验证、反驳、取代、归属等），可查询、可追溯。 |
| **Entity（实体）** | Profile 定义的语义对象（如 artifact / issue / decision / claim / fact）；有稳定标识与类型。 |
| **Profile（领域画像）** | 一组声明式的领域定义：实体类型、关系类型、事件类型、必填字段、校验规则、查询模板、保留覆盖、导出映射、版本。 |
| **Trace Core（核心层）** | 与领域无关的能力集合：身份、树、内容寻址、血缘原语、查询、保留、策略、自观测。 |
| **Manifest（清单）** | 每个 trace 的轻量索引：身份、状态、计数、产物/问题引用、完整性分数、版本信息。 |
| **Completeness（完整性）** | 期望记录项与实际记录项的比值（节点/LLM/工具/语义事件/血缘分别计算）。 |
| **Untrusted Content（未信任内容）** | 来自外部检索/文档的内容标记；消费方不得当作指令。 |
| **Boundary（执行边界）** | 类型化的执行接缝（节点/子代理/LLM/工具/MCP/API/检索/语义汇聚点）；采集只允许发生在这里。 |
| **Tool/Agent Catalogue（工具与代理目录）** | 记录工具/代理标识、版本、类别、IO 契约与默认策略的登记表；用于命名、分类、策略与覆盖审计，**不是采集的前置条件**。 |
| **Coverage Audit（覆盖审计）** | 对比"应捕获"与"已捕获"，输出盲区清单（未登记工具、绕过边界、关闭采集、丢弃、写入失败）。 |
| **Derived / Asserted Lineage（派生/断言血缘）** | 派生 = 由已有引用字段自动推导并标 `derived`；断言 = 生产者显式声明并标 `asserted`。 |

## 4. 分层功能视图与侵入性约束

```
┌────────────────────── Consumers ──────────────────────┐
│ Scout Reader │ Apiary │ 评估/回归 │ 人/运维 │ 导出器     │
└──────────────────────────▲────────────────────────────┘
                           │ 查询契约（只读）
┌──────────────────────────┴────────────────────────────┐
│ Trace Core：身份/树/内容/血缘原语/查询/保留/策略/自观测  │
└──────────────────────────▲────────────────────────────┘
                           │ Profile 注册（写时校验）
┌──────────────────────────┴────────────────────────────┐
│ Domain Profile（AlphaBee / 未来其他域）                 │
└──────────────────────────▲────────────────────────────┘
                           │ 生产
┌──────────────────────────┴────────────────────────────┐
│ 生产者适配：图节点/子代理/LLM/工具/MCP/API/脚本/定时任务 │
└───────────────────────────────────────────────────────┘
```

**三条硬边界**

1. **Core 不出现领域词汇**（artifact/issue/claim 只能出现在 Profile 与查询模板中）；
2. **Profile 不能改变 Core 语义**（只能声明与校验；Core 的 span/内容/查询行为不因 Profile 变化）；
3. **消费者只读**（写入方只有运行时；任何读取失败不影响写入）。

### 4.1 侵入性的五个维度与目标

| 维度 | 含义 | 零侵入目标 |
|---|---|---|
| **代码侵入** | 业务模块里要加 trace 调用/装饰器/注解 | 业务模块新增 trace 相关代码 **= 0 行** |
| **耦合侵入** | trace 模块 import 业务模型，或业务 import trace | 依赖单向：业务不知道 trace；trace 不知道领域 |
| **行为侵入** | 采集改变执行顺序、失败语义、状态、延迟 | 永远 fail-open；不改变任何返回/异常/顺序 |
| **配置侵入** | 每加一个工具/节点要改 trace 配置 | 新增工具/节点 **= 0 配置改动**（目录元数据除外） |
| **框架/结构侵入** | 绑定 LangGraph/MCP/某个 LLM 库 | Core 不认识任何框架；适配器在边缘 |

### 4.2 低侵入设计原则（8 条）

1. **在"边界"采集，不在"业务函数"采集**：只对类型化的执行边界埋点；业务函数内部不出现 trace 调用。
2. **自动优先于显式**：能从运行时/已有结构推导的（父子关系、耗时、状态、重试、工具名、代理名、token、产物引用）绝不要求生产者手写。
3. **未知安全（unknown-safe）**：没见过的工具/代理/事件/关系照常记录为通用类型并标"未登记"，**先记录、后归类**，绝不因不认识而丢弃或报错。
4. **注册表而非注解**：新工具只登记元数据（名称/版本/类别/输入输出契约），由边界自动捕获；不要求改工具代码。
5. **派生优先于断言**：能从已有引用字段（artifact 的上游 refs、issue 的 related step、decision 的 based_on、claim 的 evidence refs）推导出的血缘自动派生并标 `derived`；只有判断型关系（验证/反驳/取代）才要求显式断言。
6. **语义汇聚点集中发射**：artifact / issue / decision / claim 只在其**已有统一落点**发射事件，不在每个生产者里散落埋点。
7. **运行期结构而非静态 DAG**：父子关系取自运行上下文；流程重排、分支、循环、并行、子图自动反映，不维护"图结构映射表"。
8. **采集自限**：有预算、有采样、有上限、可关闭；内部失败只记录到自观测，不反噬业务。

### 4.3 非侵入采集边界目录

| 边界 | 自动记录 | 新东西如何覆盖 |
|---|---|---|
| 执行节点边界 | 节点名、起止、状态、输入/输出指纹、产生/消费实体 | 节点在装配处统一包一层；新增节点自动覆盖 |
| 子代理边界 | 代理名、父节点、轮次、工具序列 | 工厂/构建处统一注入 |
| LLM 调用边界 | 组件、模型、参数、prompt/response 引用、token、错误/重试 | 模型工厂统一挂载 |
| 工具调用边界 | 工具名/版本、入参、结果、状态、空结果 | 工具目录 + 调用边界自动捕获；未知工具走通用 span |
| MCP 边界 | 服务器/工具、任务标识、状态、产物 | MCP 适配层统一拦截 |
| 外部 API/客户端边界 | 端点、参数摘要、响应、状态、缓存 | 共享客户端统一拦截 |
| 检索边界 | 查询、命中数、结果引用、未信任标记 | 检索工具统一包装 |
| 语义汇聚点 | artifact/issue/decision/claim 的产生与引用 | 在已有统一落点发射；新类型走通用实体 |
| 守卫/缓存/预算 | 拦截、命中/未命中、超限 | 守卫/缓存中间件统一 |
| 任务入口（脚本/定时/CLI/Web） | run 身份、退出状态 | 统一入口适配；新入口不改核心 |

**关键点**：边界数量是**常数级**（约 10 类），不随业务功能增长；新增工具/节点只是"经过同一个边界"，因此天然被记录。

### 4.4 业务变化如何自动覆盖

**场景 A：新增一个工具（不写 trace 代码）**

1. 在工具目录登记元数据（名称/版本/类别/输入输出契约/是否外部 IO）；
2. 运行时经过工具调用边界 → 自动产生 tool span（args/result 引用、状态、耗时、重试）；
3. 若忘记登记：仍被通用 span 捕获，并打"未登记工具"标记，进入覆盖审计清单；
4. Scout 看到的是统一的 tool span 语义，不需要为新工具改查询。

**验收**：新增工具在 trace 中的记录完整度 = 100%（边界内），且业务代码 diff 为 0。

**场景 B：新增/重排 pipeline 节点**

1. 节点在装配处统一被包装（不是每个节点函数自己处理）；
2. 父子关系取自运行上下文，重排/分支/条件路由/循环自动反映；
3. 节点产出的 artifact/issue 在汇聚点自动形成血缘；
4. 不需要改 trace 代码，也不需要维护静态"节点→标题"映射。

**验收**：新增节点零 trace 改动；重排后 trace 树与实际执行一致。

**场景 C：引入新的 MCP 服务/外部数据源**

1. MCP/客户端边界自动捕获；
2. 未登记的服务以通用 MCP span 出现 + 标记，供目录补登；
3. 外部内容默认标"未信任"。

**场景 D：业务逻辑内部散落的调用（覆盖盲区）**

如果某个业务函数绕过共享边界直接发起外部调用（例如自己 new 一个 HTTP client），trace 不会自动捕获——这是**产品必须显式承认的边界**。产品对策：① 工程纪律"外部 IO 必须走共享客户端"；② **覆盖审计**：对比"实际外部调用"与"已捕获 span"，输出盲区清单；③ 盲区不是靠加埋点解决，而是把该路径收编到边界。

### 4.5 侵入性分级与配额（L0–L4）

| 级别 | 形式 | 允许场景 | 占比目标 |
|---|---|---|---|
| **L0** | 零改动（边界自动捕获） | 节点/LLM/工具/MCP/API/汇聚点 | ≥80% |
| **L1** | 只加元数据（工具/代理目录登记） | 新工具、新代理、外部服务 | ~15% |
| **L2** | 声明式配置（Profile/策略/开关） | 领域实体/关系/保留/脱敏 | ~5% |
| **L3** | 在控制点显式断言（判断型语义） | "验证/反驳/取代"等推断不出的关系；集中在一处 | 少量、集中 |
| **L4** | 业务代码直接调用 trace API | **禁止**（仅适配器层允许） | 0 |

产品规则：**领域模块不 import trace 模块；trace core 不 import 领域模块**；L4 只允许出现在适配器/集成层。

### 4.6 不可避免的侵入与"完全记录"的精确表述

| 无法零侵入的东西 | 原因 | 最小化形式 |
|---|---|---|
| 判断型语义（谁验证了谁、谁反驳了谁） | 无法从数据自动推导 | 在已有 decision/issue 对象上断言，集中在语义汇聚点，不在业务逻辑里散落 |
| 新工具的元数据（名称/版本/类别/IO 契约） | 需要标识与分类 | 工具目录登记（L1）；可自动推导的字段（名称/签名）不要求手填 |
| 策略选择（采样/保留/脱敏/级别） | 业务与合规决定 | 声明式配置（L2），按 Profile/类别，不按调用点 |
| 覆盖盲区识别 | 依赖"外部 IO 必须走边界"的纪律 | 覆盖审计 + 目录治理，而不是加埋点 |

> **"完全记录"的精确表述**：凡是经过已定义执行边界的调用，100% 记录；未经过边界的路径由覆盖审计发现并收编。这比"全量日志"更可信，也能防止"日志很多但关键路径缺失"的假覆盖。

### 4.7 侵入性要求与功能规格的对应

| 要求 | 对应功能规格 | 验收 |
|---|---|---|
| 非侵入采集边界 | FR-Core-11（§5） | AC-13、AC-14、AC-15 |
| 未知安全捕获 | FR-Core-12（§5） | AC-16 |
| 派生血缘 | FR-Core-13（§5） | AC-2、AC-19 |
| 采集预算与开关 | FR-Core-14（§5） | AC-18 |
| 依赖方向约束 | FR-Core-15（§5） | AC-17 |
| 工具/代理目录 | FR-Adapter-04（§7） | AC-13、AC-16 |
| 覆盖审计 | FR-Adapter-05（§7） | AC-16、§13 指标 |
| 多入口一致 | FR-Adapter-06（§7） | AC-1、AC-13 |

## 5. Trace Core 功能规格

### FR-Core-01 Trace 身份与生命周期（P0）

**能力**

- 每次执行创建唯一 trace，绑定：trace_id、run_id、task_id、session_id（可选）、symbol、as_of、profile id + version、schema_version。
- 记录执行元信息：代码版本、配置指纹、模型版本、prompt 版本、数据快照引用、环境标识（机器/进程可选）。
- 生命周期状态：`running / succeeded / failed / partial / cancelled / aborted`；关闭后状态不可变（只允许追加"更正"事件）；异常中断的 trace 必须被标记为 `partial` 并保留已写入部分。
- 支持"同一 run 重试/重跑"生成新 trace，并通过 `supersedes` 关系关联旧 trace，便于对账。
- 迟到记录容忍窗口：关闭后到达的合法记录可追加（标记 late），窗口由策略配置；窗口外拒绝并计数。

**产品规则**

- trace 一旦创建，profile 版本固定，不允许中途切换；
- 同一 trace 的写入必须幂等：相同记录重复提交不产生重复 span/事件（按记录标识去重）；
- 读取方可随时读已提交内容；未关闭的 trace 显示"进行中"与已知完整性。

### FR-Core-02 Span 模型（P0）

**能力**

- 支持 Span 类型（可扩展，至少覆盖）：`run / node / agent / llm / tool / mcp / api / retrieval / artifact / decision / issue / guard / cache / budget / custom`。
- 每个 Span 记录：标识、父标识、类型、名称、所属节点、所属代理、开始/结束时间、耗时、状态、尝试序号与重试来源、属性、内容引用、关联实体引用。
- 状态：`ok / error / timeout / cancelled / skipped / partial`；错误记录错误类型、消息摘要、是否可重试。
- 层级：每个 span 至多一个父；孤儿（父缺失）挂到 run 并打标记；并行 span 按开始时间排序。
- 事件 vs 子 span 的产品判据：**有持续时间的执行单元用 span；瞬时语义记录用 event**（例如"artifact 产生"是 event，"工具调用"是 span）。
- 属性（attributes）按类型有允许清单；不得放超长内容（内容必须走内容对象），避免"属性当存储"。
- 单次执行的 span 数量与单 span 属性大小有上限，超限降级并记录"截断/丢弃"标记。

**产品规则**

- 节点 span 必须记录输入指纹与输出指纹（内容哈希）及状态；
- LLM span 必须记录：组件/模型/参数、prompt 引用、response 引用、token 用量、耗时、状态、请求标识；
- 工具 span 必须记录：工具名/版本、入参引用、结果引用或摘要、状态、耗时；
- 重试必须保留全部尝试（attempt 链），不得只保留最后一次。

### FR-Core-03 内容对象与分级（P0）

**能力**

- 任何需要保留的文本/结构化内容以内容对象保存，按内容哈希寻址；相同内容只存一份（去重）。
- 内容对象不可变；可被 span/event 以引用方式关联；可单独取回（受访问策略约束）。
- 保留级别：
  - **L0**：引用（标识 + 类型 + 哈希），不含内容；
  - **L1**：元数据（大小、类型、摘要预览、哈希、产生者、时间）；
  - **L2**：内容全文（prompt/response/工具结果/结构化输出）；
  - **L3**：原始快照（原始 API 响应、文档原文、MCP 产物）。
- 分级策略：默认级别由策略配置（建议 L1 全量 + L2 按需/采样 + L3 仅失败/审计/显式请求）；同一 span 的不同内容可分级不同。
- 体积控制：单内容上限、单 run 预算、超限截断并打标记；大内容分块但逻辑上仍是一个对象。
- 预览：列表/清单视图仅返回有限预览（长度可配），避免把全文带进查询结果。
- 脱敏：保存前执行脱敏规则（密钥、凭据、个人敏感字段、超限隐私字段）；被脱敏的对象必须标记"已脱敏"并记录规则版本。
- 外部内容（检索/文档/网页）必须标记为"未信任"，消费方需以数据对待。
- 生命周期：内容对象可被保留策略单独过期；过期后引用保留、内容取回返回"已过期"状态。

### FR-Core-04 血缘原语（P0）

**能力**

- 支持三类参与方：实体（Entity）、活动（Activity = span/trace）、代理（Agent = 执行者/模型/人）。
- 支持关系类型（可扩展的固定词汇）：`generated_by / used / derived_from / validated_by / refuted_by / supersedes / attributed_to / informed_by / part_of`。
- 每条血缘边记录：起点、终点、关系类型、断言者（哪个 span/事件产生该边）、时间、证据引用（可选内容对象）、置信/确定性标记（确定规则 / LLM 判断）、Profile 版本。
- 血缘边是可查询的一等对象：支持上游/下游遍历、按关系过滤、按实体聚合、影响面分析、环检测。
- 血缘边必须可追溯到产生它的事件（谁断言、依据什么内容）。

**产品规则**

- 边的两端必须是已登记实体或已存在 span/event；未知端点进入"隔离区"并标记，不阻断写入；
- 同一对实体允许多条不同关系的边；相同关系重复断言需幂等；
- 血缘不要求完整覆盖所有实体，但必须能报告"覆盖率"（多少 artifact/claim 具备上游引用）。

### FR-Core-05 语义事件目录（P0）

系统必须支持并鼓励生产者发出以下事件（完整字段在附录 B）：

| 事件 | 何时产生 | 必带引用 |
|---|---|---|
| `run.start / run.end` | 执行开始/结束 | run、状态、摘要 |
| `node.start / node.end` | 节点进入/退出 | 节点、输入/输出指纹、状态 |
| `agent.start / agent.end` | 子代理开始/结束 | 代理、父节点 |
| `llm.error` | LLM 失败/超时/解析失败 | 组件、错误、重试次数 |
| `tool.error` | 工具失败/超时 | 工具、错误、是否降级 |
| `artifact.produced / artifact.consumed` | 产物产生/被消费 | artifact、上游引用 |
| `issue.emitted / issue.resolved` | 问题出现/消解 | issue、类别/严重度、来源 span |
| `decision.emitted` | 决策产出 | decision、输入引用 |
| `claim.emitted` | 结论/主张产出 | claim、证据引用 |
| `fallback` | 触发降级/回退 | 触发点、原因、替代路径 |
| `degraded` | 数据/洞察/报告降级 | 降级层级、原因 |
| `cache.hit / cache.miss` | 缓存命中/未命中 | 缓存键、来源 |
| `empty_result` | 工具返回空/无匹配 | 工具、查询参数摘要 |
| `retry` | 重试发生 | 原 span、尝试序号、原因 |
| `budget.exceeded` | 预算/配额超限 | 预算类型、阈值、当前值 |
| `guard.block` | 守卫拦截（如搜索限制） | 规则、输入摘要 |
| `lineage.edge` | 血缘边断言 | 两端、关系、证据 |

**产品规则**

- 事件不得替代 span；有持续时间的工作必须同时有 span；
- 事件必须携带来源（哪个 span/节点/代理）；
- 未识别事件类型进入"未知事件"桶并计数（不得静默丢弃）。

### FR-Core-06 查询能力（P0/P1）

作为**只读契约**，系统必须提供以下功能（不含实现接口形式）：

| 编号 | 能力 | 输入 | 输出 |
|---|---|---|---|
| Q1 | 按条件找 trace | 标的/日期/任务/状态/标签/profile | trace 清单（含 manifest 摘要、分页） |
| Q2 | 取 trace 清单 | trace_id | 身份、状态、版本、计数、完整性分数、实体/问题摘要 |
| Q3 | 取 span 树 | trace_id、过滤条件、深度限制 | 分层 span 列表（含关键属性与内容引用） |
| Q4 | 取 span 详情 | span_id | 属性、事件、内容引用、尝试链 |
| Q5 | 取事件 | trace_id、类型、时间窗 | 事件列表（含来源） |
| Q6 | 取内容对象 | 内容标识 + 视图（预览/全文/脱敏视图） | 内容或过期/无权限状态 |
| Q7 | 血缘遍历 | 起点实体/span、方向、关系过滤、深度 | 血缘子图/边列表（含断言者与证据） |
| Q8 | 跨 trace 搜索 | 实体标识/内容哈希/关键属性 | 出现的 trace/span 及上下文摘要 |
| Q9 | 差分 | 两个 trace_id + 对齐键 | 节点/内容/状态差异与漂移分类 |
| Q10 | 聚合指标 | 时间窗、维度（节点/工具/模型） | 计数、token、延迟分位、错误率、降级率 |
| Q11 | 导出/归档/删除 | 范围、级别、策略 | 导出产物或删除审计记录 |
| Q12 | 完整性报告 | trace_id | 期望/实际记录项、缺失项、丢帧计数 |

**产品规则**

- **索引优先**：任何面向 Scout/人的查询先返回清单/摘要，内容按需下钻，避免把大量内容带入上层上下文；
- 查询结果必须有稳定标识，便于二次引用；
- 单次查询有结果上限与分页，超限需显式提示；
- 一致性：同一 trace 内"写后读"可见；跨 trace 的索引允许秒级延迟，但必须暴露"索引截至时间"；
- 所有查询失败返回明确状态（而非空结果）；读取方据此区分"没有"与"读不到"。

### FR-Core-07 差分与对齐（P1）

**能力**

- 对齐键（由 Profile/调用方提供）：例如"同标的 + 同 as_of + 同输入指纹"；
- 差分维度：节点集合、span 集合、状态、耗时、token、内容哈希、语义事件、血缘边；
- 漂移分类：模型变化 / prompt 变化 / 代码版本 / 配置 / 数据快照 / 输入本身 / 未解释；
- 输出分为"摘要（变化点清单）"与"下钻（具体 span/内容差异）"两级。

**产品规则**

- 差分只对"可比较的 trace"生效；不可比较时明确说明原因（输入、快照、版本不同）；
- 差分结论必须指向具体 span/事件，不得只有"整体不同"。

### FR-Core-08 保留、采样与生命周期（P0 策略、P1 自动化）

**能力**

- 分级保留：L0/L1/L2/L3 各自 TTL；可按 Profile/标的分组；
- 采样：按 run 类别（常规/异常/首次/显式请求）控制 L2/L3 采集比例；
- 容量治理：单 run 预算、单日预算、全局配额；超限时降级（L2→L1）并打标记，不得静默丢失；
- 归档：过期前可导出为不可变归档；归档后内容可按策略删除；
- 删除：支持按范围删除，必须留存删除审计（谁、何时、范围、原因）；
- 保留期内不可变；到期后引用保留、内容失效。

**产品规则**

- 任何降级/丢弃都必须可观测（计数 + 标记），不允许静默；
- 保留策略变更只影响未来运行或未来过期判断，不得追溯删除已有归档。

### FR-Core-09 访问控制与数据边界（P0 最小、P1 完善）

**能力**

- 写入方唯一：运行时；其他系统不得写入；
- 读取方分角色：Scout（只读、按需、可限制查询预算）、Apiary（只读/快照）、人（只读、可导出）、导出器（只读、可限定字段）；
- 内容访问分级：L2/L3 的读取需要显式授权（默认 Scout 可读 L2 的预览与受限全文，L3 需请求）；
- 未信任内容标记贯穿查询结果；
- 密钥/凭据永不入库；敏感字段按脱敏规则处理；
- 预留多项目/多 Profile 的逻辑隔离（同一存储可按 profile 命名空间分离）。

### FR-Core-10 Core 自身可观测性（P0）

- 记录自身的写入延迟、失败计数、丢帧、降级、内容体积、查询延迟、查询失败；
- 每个 trace 提供完整性分数（按记录类别分别计算）；
- 提供"健康状态"摘要供运维与消费者判断可用性；
- 自身写入失败绝不影响业务执行（fail-open），但必须留下可观测告警。

### FR-Core-11 非侵入采集边界（P0）

- 采集只允许发生在类型化执行边界（节点/子代理/LLM/工具/MCP/外部 API/检索/语义汇聚点）；业务函数内部不得出现 trace 调用。
- 边界目录与统一注入点由 Core/适配层提供；边界数量应保持常数级，不随业务功能增长。
- 新增工具/节点/入口不得要求修改 Core 或业务代码；仅允许登记元数据或零改动。
- 采集必须可独立关闭（全局/按 run/按类别），关闭后行为与无 trace 版本一致。

### FR-Core-12 未知安全捕获（P0）

- 未登记的工具/代理/事件/关系照常记录为通用类型，并标记"未登记"。
- 写入时不得因未知类型拒绝或抛错；归类延迟到 Profile/消费侧。
- 未登记项进入"覆盖审计"清单，可统计、可指派处置。
- 未知事件进入"未知事件"桶，不静默丢弃。

### FR-Core-13 派生血缘（P1）

- 能从已有引用字段推导的关系（artifact 的上游 refs、issue 的 related step、decision 的 based_on、claim 的 evidence refs）自动派生，并标记 `derived`（含推导规则版本）。
- 判断型关系（`validated_by / refuted_by / supersedes` 等无法自动推导的）由生产者在语义汇聚点显式断言，标记 `asserted`。
- 派生的边必须可解释（来源字段 + 规则）；不得把派生边伪装成断言边。

### FR-Core-14 采集预算与开关（P0）

- 支持全局/按 run/按类别的开关与级别；采集失败与超限必须 fail-open。
- 单 run/单记录/单内容上限；超限降级并标记（不得静默）。
- 采集自身产生的内部调用不进入业务 trace（避免自引用噪声）。

### FR-Core-15 依赖方向约束（P0）

- 领域模块不得 import trace 模块；trace core 不得 import 领域模型或框架。
- 领域与 trace 的连接只允许发生在适配器/集成层。
- 该约束是产品级规则，必须有依赖审计手段（静态检查/构建门禁），并作为验收项。

## 6. Domain Profile 功能规格

### FR-Profile-01 Profile 内容（P0）

一个 Profile 必须能声明（不含实现形式）：

1. **实体类型**：名称、标识规则、必填字段、可选字段、字段类型与校验；
2. **关系类型**：允许的关系、两端实体类型约束、方向语义；
3. **事件类型**：扩展事件与必填字段（Core 事件不可重定义）；
4. **属性允许清单**：各 span 类型可带的领域属性；
5. **查询模板**：面向该领域的预置查询（例如"找被降级的报告 run"）；
6. **保留覆盖**：按实体/内容类型的 TTL 与级别覆盖；
7. **脱敏规则**：领域敏感字段；
8. **导出映射**：到 OTel / OpenLineage / PROV / Langfuse 的字段映射；
9. **校验样例**：合法/非法样例（用于注册时校验与回归）；
10. **版本与变更记录**。

### FR-Profile-02 注册、版本与兼容（P0）

- Profile 必须注册后才能用于写入；注册时执行校验：类型完整性、关系端点合法性、必填字段、样例通过；
- Profile 有独立版本；trace 创建时固定 profile id + version；
- Core 版本与 Profile 版本有兼容矩阵；不兼容时拒绝注册或拒绝新 trace（不拒绝读取旧 trace）；
- Profile 变更不得改变 Core 的 span/内容/查询行为；只影响校验、模板、保留覆盖与导出映射；
- 支持"隔离区"：写入时遇到未注册实体/关系/事件，记录并标记隔离，不阻断 run；隔离项可被查询与统计。

### FR-Profile-03 多 Profile 共存（P1）

- 同一部署可注册多个 Profile（例如 AlphaBee 研究、未来的数据管线）；
- trace 按 profile 命名空间隔离；
- 消费者按 profile 选择查询模板与实体模型；Core 查询能力对多 Profile 一致。

### FR-Profile-04 AlphaBee Profile v1 的范围（P0）

必须覆盖：

- 实体：fact / observation / artifact（含类型与角色组）/ decision / issue / claim / evaluation；
- 关系：artifact 由哪个 node/工具产出（`generated_by`）、被哪个下游节点消费（`used`）、claim 的证据引用（`derived_from`）、claim 被验证/反驳（`validated_by/refuted_by`）、issue 的来源（`generated_by`）、旧 artifact 被新 artifact 取代（`supersedes`）；
- 领域字段：标的、期间、口径、来源、时点、修订单、派生/直报、偏离分类（D1–D5）；
- 查询模板：口径异常、静默降级、结论失配、证据缺口、覆盖盲区、成本异常、重试链、回归漂移（8 类，对应 Scout 的发现场景）；
- 保留覆盖：报告/claim 类内容更长，原始检索内容更短。

### FR-Profile-05 通用性验收（P1）

Profile 分层成立的产品验收（不是"看起来通用"）：

1. **第二生产者**：另一个管线（数据抓取或跟踪调度）在不修改 Core 的前提下接入并产出合法 trace；
2. **第二消费者**：一个独立的回归/差分工具仅通过查询契约即可使用；
3. **第二 Profile**：用声明方式定义另一个领域（例如数据管线 job/dataset）并通过注册校验；
4. 三条全部通过，才允许对外称"Core 可复用"。

## 7. 生产者与消费者适配（功能要求）

### FR-Adapter-01 生产者覆盖（P0）

系统必须支持在以下执行单元上产生 span / 事件（通过适配方式，不在本文规定实现）：

| 执行单元 | 必须记录 |
|---|---|
| 图节点 | 开始/结束、状态、输入指纹、输出指纹、耗时、产生/消费的实体 |
| 子代理 | 代理标识、父节点、轮次、工具序列摘要 |
| LLM 调用 | 组件、模型、参数、prompt 引用、response 引用、token、耗时、错误/重试 |
| 工具调用 | 工具名/版本、入参引用、结果引用、状态、耗时、空结果标记 |
| MCP 调用 | 服务器/工具、任务标识、状态、产物引用 |
| 外部 API | 端点、参数摘要、响应引用、状态、耗时、是否缓存 |
| 检索/网页 | 查询、命中数、结果引用、未信任标记 |
| 脚本/定时任务 | run 身份、节点等价单元、退出状态 |
| 语义产出 | artifact/issue/decision/claim 事件与血缘边 |

**覆盖要求**：一次"完整" run 至少包含 run span + 全部节点 span + 全部 LLM 调用 + 全部工具调用 + 全部语义产出事件；覆盖率必须可报告。

### FR-Adapter-02 消费者适配（P0/P1）

- **Scout Reader**：索引优先、按需下钻、查询模板、证据引用（见 §8）；
- **Apiary**：按快照/导出读取 trace 摘要与发现证据（P1）；
- **评估/回归**：使用 Q9 差分与 Q10 聚合（P1）；
- **人**：只读清单 + 下钻；
- **导出器**：OTLP / OpenLineage / PROV / Langfuse（P2，见 §7.3）。

### FR-Adapter-03 互操作与导出边界（P2）

- **OTel 形状**：Core 字段命名对齐 OTel Trace/GenAI 语义约定（pin 版本），但**不依赖** OTel SDK/Collector；可选 OTLP 导出；
- **Langfuse**：只作为下游视图/评估导出，**不是事实源**；导出失败不影响采集，也不影响 Scout；
- **OpenLineage**：只导出"数据访问 → artifact"层，不把研究论证塞进 dataset 概念；
- **PROV**：血缘关系词汇可用 PROV 子集表达；不要求上图形数据库；
- **导出内容控制**：默认只导出 L0/L1；L2/L3 导出需显式授权。

### FR-Adapter-04 工具/代理目录（P0）

- 提供工具/代理的目录登记：标识、别名、版本、类别、输入输出契约、是否外部 IO、默认采集级别。
- 目录用于命名、分类、默认策略与覆盖审计；**不是采集的前置条件**。
- 未登记仍可被通用捕获；新工具接入不得要求改适配器/核心。
- 目录变更可版本化，旧 trace 仍按当时版本解释。

### FR-Adapter-05 覆盖审计（P1）

- 对比"应捕获（目录/图结构/调用统计）"与"已捕获（trace）"，输出盲区清单。
- 盲区分类：未登记工具、绕过边界的外部调用、被关闭的采集、采样/预算丢弃、写入失败。
- 每个盲区可指派、可跟踪、可关闭；盲区不得静默存在。

### FR-Adapter-06 多入口一致（P0）

- CLI / Web / 脚本 / 定时任务 / 未来入口使用同一套边界与身份规则。
- 新增入口不得要求改 Core；入口差异只允许在适配层。
- 所有入口的 trace 可用同一查询契约读取。

## 8. Scout 消费契约（功能）

### FR-Scout-01 索引优先与按需下钻（P0）

- Scout 首先获取：候选 trace 清单 → 目标 trace 的 manifest/完整性 → 相关节点与事件摘要；
- 只有需要时才取内容对象（L2/L3），并受上下文预算约束；
- 每次查询返回稳定标识，便于在发现卡中引用。

### FR-Scout-02 八类发现查询（P1）

系统必须支持（通过查询模板或组合查询）以下发现场景：

| # | 发现场景 | 查询要点 |
|---|---|---|
| 1 | 口径/期间混用、stale、单位错 | 事实与声明的领域字段 + 来源 + 时点；跨 artifact 对比 |
| 2 | 静默降级/回退/空结果 | fallback/degraded/empty_result 事件 + 触发 span |
| 3 | 论证失配（状态/后验/EV/结论矛盾） | 相关 decision/claim/artifact 的字段与血缘 |
| 4 | prompt 不服从（字数/格式/重复） | LLM span 的 prompt/response 引用 + 解析结果 |
| 5 | 成本/延迟异常 | 按节点/工具/模型的聚合 |
| 6 | 覆盖盲区（窗口不可用、缺失数据） | 空结果事件 + missing/degraded 记录 |
| 7 | 重试/失败链 | retry 事件 + attempt 链 + 工具错误 |
| 8 | 回归漂移 | 同输入两次 trace 的差分与分类 |

### FR-Scout-03 证据规则（P0）

- 任何发现必须能引用 trace/span/event/content 标识；无引用的发现视为无效；
- 发现必须标注"已证实/推断/不确定"，并区分"读到证据"与"没读到"；
- 未信任内容必须显式标注，且不得被当作指令。

### FR-Scout-04 预算与分页（P1）

- 查询有结果上限、分页与超时；超预算返回部分结果 + 未完成说明；
- Scout 的 trace 查询预算可配置（按会话/标的/时间窗）。

## 9. 配置与策略（功能）

系统必须提供以下可配置项（不含具体配置格式）：

| 配置 | 作用 | 默认建议 |
|---|---|---|
| 总开关 | 是否采集 trace | 开（fail-open） |
| 级别 | L0/L1/L2/L3 默认组合 | L1 全量 + L2 采样 + L3 失败触发 |
| 采样 | 按 run 类别/标的/异常的控制 | 常规 10%、异常 100%、首次 100% |
| 保留 | 分级 TTL、归档策略 | L1 90 天、L2 14–30 天、L3 7 天（待校准） |
| 容量 | 单 run/单日/全局预算 | 超限降级并标记 |
| 脱敏 | 规则集与版本 | 密钥永不出库；外部内容标记 |
| 访问 | 角色/范围/内容级别 | Scout 只读、L3 需请求 |
| Profile | 激活的 Profile 与版本 | AlphaBee v1 |
| 导出 | OTLP/Langfuse/OpenLineage 开关 | 默认关 |
| 失败策略 | 采集失败行为 | 永远 fail-open |

**策略优先级**：单次 run 显式覆盖 > Profile 覆盖 > 全局默认；策略变更对已写入内容不追溯（保留/删除策略除外，需审计）。

## 10. 非功能需求

| 维度 | 要求 |
|---|---|
| 开销 | 采集不得显著改变 run 的耗时/失败率；写入应为非阻塞或低阻塞；单次记录有上限 |
| 容量 | 默认级别下单 run 元数据开销可接受（数十万级记录以内）；提供容量预估与配额 |
| 查询 | 清单/摘要查询应在秒级；下钻可接受更慢；所有查询有上限与分页 |
| 可用性 | trace store 不可用时，业务 run 照常完成；Scout 明确报"读不到"而非"没有" |
| 崩溃安全 | 进程中断后已写内容可读；未完成 trace 标记 partial；不得因写入中断损坏已有记录 |
| 幂等 | 重复提交相同记录不产生重复；重试不重复计费/计数 |
| 时间 | 时长用单调时钟；时间戳用墙钟并标注时区；允许时钟偏移检测 |
| 演进 | schema 版本化，新增字段兼容旧读取；Profile 独立版本；不兼容变更需迁移说明 |
| 可移植 | 导出格式标准化；不绑定单一后端；本地部署可离线运行 |
| 隐私 | 脱敏、最小化、保留期限、删除审计；外部内容标记未信任 |

## 11. 边界与反模式

**明确不做**

- 不做 UI/看板/搜索前端（可由外部后端提供）；
- 不做评估平台（数据集/评分/标注）；
- 不做执行回放与状态重建；
- 不做实时干预（不改变执行路径）；
- 不记录"结论摘要"替代证据；
- 不与 canonical facts 竞争事实源地位。

**反模式（必须避免）**

- 把 trace 写成第二个 Langfuse/OTel 后端（重复建设、查询被后端绑架）；
- 让采集阻塞主链，或把"日志写失败"当业务失败；
- 把大内容塞进属性/索引；
- 只记录摘要（重蹈"摘要偏差"）；
- 用未版本化的自由字段做 Scout 契约；
- 血缘边由消费者推断而非生产者断言；
- 无限保留、无采样、无容量治理；
- 把 Profile 专有词汇写进 Core；
- 在业务函数里直接调用 trace API（L4 侵入；仅适配器允许）；
- 用 monkeypatch 全局劫持第三方库来"自动"采集（不可控、不可解释）；
- 为每个新工具写专门的 trace 配置/注解（新工具必漏）；
- 用字符串/正则解析业务输出"猜"语义（脆弱、不可审计）；
- 把"未登记"当错误、拒绝写入（应为未知安全 + 隔离）；
- 让采集路径依赖前端（CLI/Web）事件流，而非运行时边界。

**与 Langfuse 的边界**：Langfuse 负责通用 LLM 观测视图、成本/评分/Prompt 管理；本产品负责领域证据链与 Scout 查询契约。二者通过导出连接，Langfuse 永远不是事实源。
